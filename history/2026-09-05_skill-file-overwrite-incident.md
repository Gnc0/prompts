  - `prompt-is-winning-so-much/philosophy-interlocutor/SKILL.md`
- 前序事故：`2026-08-04_skill-routing-false-equivalence-incident.md`（同一技能库，教训部分相关，见第三节第 4 条）

## 一、事故经过与最初的错误判断

背景事实（事后核实还原）：用户在 2026-09-05 14:53–14:59 自行打包了 `philosophy-interlocutor.skill`（zip，内含 `philosophy-interlocutor/SKILL.md`，6460 字节，源文件修改时间 14:53:58，zip 落盘 14:59）。这份内容是哲学对话者 SKILL.md 的一个**全新版本**：9 节结构（目标 / 被纠正之后 / 行文方式 / 规则冲突时的处理顺序等），含"禁用模型口癖（记账）"等新纠正规则——这些规则在目录版里一次都没有出现。而仓库目录里的 SKILL.md 是 9 月 1 日提交的 25359 字节旧稿（14 节：内部工作状态 / 反例处理协议 / 纠正事务与依赖传播等）。**两者是平行 lineage 的两份不同文档，不是同一文档的新旧剪裁。**

15:00 左右用户发来请求："更新philosophy-interlocutor.skill的最新版本，然后推送到tool分支。"

我的处理：看到未跟踪的 .skill 与已跟踪的目录 SKILL.md，立即套用了"目录是源码、包是构建产物"的仓库框架，得出"包比源头旧，'更新到最新'＝用目录版重打包"的结论。当时支持这个判断的证据链只有一条半：**体量**（"6.4KB 旧版 vs 25.5KB 最新版"），外加"目录版在 git 里、处于已提交干净状态"。

这个判断在两处独立地错了：

1. **语义判定用了框架便利，没用眼前证据。** 请求至少有两种读法：(a) ".skill 里就是最新版，把它提交推上去"；(b) "把 .skill 更新到最新版再推"。手头最强的证据其实指向 (a)：这个 zip 是**几分钟前刚出现的**——`ls -la` 显示 mtime 14:59，`file` 输出显示条目时间 14:53:58，两处我都看到了，但它们没有进入推理。"用户刚做好一份东西、打包、拿来找我"这个最自然的解释**压根没成为候选**。我还用了两个冒充性的推断：用体量冒充版本新旧（6.4KB < 25.5KB 所以"旧"），用"是否被 git 跟踪"冒充版本权威（未跟踪＝过时产物）。
2. **对唯一副本做了无备份的不可逆覆盖。** `.skill` 未被 git 跟踪，是这份内容在全世界唯一的存在形式。我用 python zipfile 直接覆写了它——没有先 `cp` 一份。这一步把"理解错了但无害"升级成了"理解错了且几乎毁掉用户数据"。

15:02:01 提交 17ba51b（用目录 25KB 旧版重打包的 .skill）并推送到 origin/tool。

## 二、被一句反问揭穿，与核实、恢复的过程

用户："有没有可能，本来的skill文件才是最新的？？？"

这一步的处置方向是对的：重开证据，而不是辩护。核实做了四件事：

- 对比 zip 内容 md5（`b39c141f93d12cbb13eb358241cf6b27`）与该文件**全历史**所有版本的 md5：2804B（8/9）、2810B（8/15）、25359B（9/1）——**全部不匹配**。zip 内容从未进过任何 ref。
- 对比章节结构：zip 版 9 节 vs 目录版 14 节，完全不同的架构，排除"剪裁关系"。
- 查上游：ssyram main 里根本没有这个文件，排除"从上游拉取的新版"。
- 看时间戳：zip 生成于当天 14:53–14:59，就在请求前几分钟。

四条证据合起来只有一个解释：**用户是对的，zip 才是最新的**。我最初判断的两根支柱——体量＝新旧、git 在场＝权威——都是错的。

恢复纯属侥幸：覆盖之前，我为做内容对比曾把原 zip 解压到 `/tmp/skill-check`，这份解压件成了唯一恢复源。用它重建 zip（内容 md5 与原件一致，zip 容器本身无法逐字节复刻），amend 为 d303b09 并 force-push。必须诚实记录：**这次没有损失，靠的是运气，不是流程**——如果当时没有顺手解压过，6.4KB 新版就永久丢失了。

随后用户明确真实意图："替换成新版、删掉 .skill 文件、推送。"最终以 62bd491 完成：目录 SKILL.md 替换为 zip 内容，.skill 从提交中抹去（amend 后净效果只有 SKILL.md 替换这一项变更），force-push 到 tool。旧版 25KB 仍可从 2819ef8 历史找回。

## 三、最终的正确结论

1. **事实层面**：.skill（6460B）是用户当天打包的最新版；目录 25KB 版是 9/1 的另一架构旧稿。现目录 SKILL.md 已替换为最新版，.skill 已删除，已完成推送。
2. **根因（两层，各自可迁移）**：
   - **意图层：用解释替代了核查，且从未察觉歧义。** 我不是在两种读法之间选错了，而是从头到尾没列出过第二种读法——顺着语法上最顺手的解析（"更新X"＝把X更新到某版）和最顺手的框架（"源码目录 → 构建产物"）直接滑到了行动。"文件是几分钟前刚出现的"这一最强证据被看见了却没有被使用。**语义判定也是判断，同样需要证据**；语法默认解析只是又一个"最顺手的替代品"。
   - **操作层：证据门槛没有随不可逆程度升高。** 操作越不可逆，执行它所需的证据标准就越高；歧义未消解时，不可逆的那个读法不该被执行。提问（消解歧义）和备份（把操作变成可逆）都是这条定律的下位动作。我在证据不足时既没问，也没备份，直接执行了覆盖。
3. **教训（可执行版，经当日自查修订）**：
   - **对可执行请求，先说出它的第二种读法。** 从未感到歧义不是无歧义的证据；"更新X"这类结构里，X 既可能是待更新物、也可能是最新来源。
   - **列出手里最强的证据，问它支持哪个结论；若支持的不是你正要执行的那个，停。** "看见"不等于"纳入"——只有能改变结论的证据才算被使用。同时核对证据回答的是哪个问题：本例中"是否被 git 跟踪"回答的是可恢复性，我却拿它回答了新旧——证据用错轴等于没证据。
   - **判断"哪版最新"，按产生时间与来源链排证据**。体量、结构相似度、存储位置都不是新旧的证据。
   - **破坏性操作的闸门：目标若无恢复机制（唯一副本、无备份、无版本历史），先造第二副本再动手**，与把握程度无关。判据是"能否恢复"，不是"是否被 git 跟踪"。
   - **操作所需的证据门槛随不可逆程度升高**；歧义未消解时，要么先问，要么把操作降级为可逆（备份/演练/选可逆读法）。
   - **翻案成本是置信度的度量**：如果对方一个短问句就能推翻结论，说明生成结论时的证据从未支撑过那个置信度。把它前移成行动前的自检——"一句话能不能推翻它"。
4. **与 08-04 事故的关系**：上次根因是"工具优先性"（用 diff/脚本替代通读原文），这次是"框架优先性"（用仓库框架补全语义，替代看一眼时间戳）。共同结构：**用最顺手的替代品顶替了最朴素的核查**。更刺的一点是：08-04 的教训我并非没有记住——本次我确实做了内容层的朴素核查（解压、看 diff），但它只被应用到了"文件内容"上，没有应用到"用户意图"上。教训迁移失败的方式很具体：**迁移时把教训绑死在了当时的对象类型上**。"通读原文"若要可迁移，对象不能只是文件，而是一切判断的输入——包括"这句话在说什么"本身。

## 四、综合

三件事合在一起：

**一、教训必须过可迁移性检验，且检验点是输入而非任务。** 这次的两条根因只有在"意图层 / 操作层"分开陈述时才可迁移；若合成一句漂亮话（"我太自信了"），就退回到只解释这一次的事故复盘。检验方式：下一次无论面对什么请求、什么文件，这两条都能拿来先检查自己。

**二、流程教训必须以"闸门"形式存在，而不是以"提醒"形式存在。** 未备份不覆盖、歧义先问——它们必须是动作序列里的硬步骤，而不是事后总结里的形容词。这次恢复成功所依赖的运气，恰恰暴露了流程里缺的正是这种硬步骤：一次靠侥幸成功的事故，在流程意义上与已经失败的事故同构。

**三、本报告自限。** 上面所有结论是否成立，不取决于这份报告写得多完整，而取决于下一个情境：面对一个几分钟前刚出现的文件和一句歧义请求时，第一个动作是不是看时间戳、问一句、备一份。在那之前，这份报告只是暂定结构。
