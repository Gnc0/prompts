# Role

当你要**用测量、而不是凭感觉**把一个提示词（distiller / agent system-prompt / 工具描述 / 分类器 prompt / 任何 prompt）改到更好时，用这套方法：**围绕"真实消费这个提示词的系统"，建一个尽量小、可反复跑的评测循环。**

本 skill 是**建议性**的——给的是骨架和判断点，不是强制清单；样例、度量、脚本都**按你的被测对象实例化**。骨架五件：**① 定测试对象 → ② 建核心输入(fixture) → ③ 建测试执行器(runner) → ④ 定评判/度量 → ⑤ 装配 + 诚实迭代。**

贯穿全程的一条信念：**"更好"必须是量出来的、稳定分离的、无回归的、信息没丢的；量不出稳定优势就诚实说"没赢"，别硬凑一个假赢家。**

---

## ① 测试对象

- **测"消费这个提示词的真实系统的输出/行为"，不测"提示词文本读起来好不好"**——提示词是通过它下游产生的东西被评判的。
- **候选隔离，生产不动**：用 variant / sidecar 副本（如 `--force-variant`，或跑真 agent 时 `-e 副本入口`），测完再决定换不换。
- **增量改、不全盘重写**：新能力靠加约束长出来；每个候选和当前版 `diff`，确认**没删掉原有条款、也没意外扩大范围**——重写最爱悄悄漏掉"为别的目的服务"的条款。

## ② 核心输入（fixture）

- **先从真实失败 / 高价值现场挖**，别凭空造：真实 session、日志、出过问题的输入。真实案例 > 编造。
- **两类缺一不可**：**判别样例**（目标性质在此有分歧、能把候选分开）+ **回归护栏样例**（专测这个修法可能误伤什么）。构造样例只在"要编码一个精确的边界/攻击"时补。
- **确认 fixture 真的走到被测路径**：别选会被 bypass / 提前短路掉的输入（除非你就是要测那个）。
- fixture 形状**随对象变**：distiller 是（system-prompt + history + tool-result）三元组；agent prompt 是（task + 上下文 + 工具列表）；分类器是（文本 + 候选标签）。

## ③ 测试执行器（runner）

- **一个配置驱动的并行脚本**，跑 `提示词变体 × 模型/config × fixture × 重复次数` 的叉积，落：每次原始产物 + 结构化分数 + 汇总表。
- **推荐形态**：单文件脚本 + 一份 config（模型/endpoint/变体/reps）+ 命令行开关；无外部重依赖，任何 OpenAI-compatible endpoint 能跑。
- **接真实系统的点只留一个、失败要 loud**（别静默吞错）；秘钥不进提交文件。
- **执行器形状随对象弹**：被测是"渲染后调一次模型"就调函数；被测是 agent system-prompt / 工具描述，就得**跑一整个 agent turn**（非确定、要更多 reps；parser 抽的是工具调用/动作序列，不是纯文本）。

**推荐的 runner 骨架**（架构通用，照抄；只改标了 customize 的点）：
- **config**（一份 JSON）：`{"configs":[{"name":"m1","model":"…","maxTokens":8192,"variant":"baseline"}, …]}`；endpoint / key 从 env 读，**不进提交文件**。
- **CLI 开关**：`--configs <f>` · `--force-variant <X>`（所有 config 改用变体 X 的 prompt 文件）· `--samples N`（每输入重复 N 次测稳定性）· `--judge <model> --judge-k K`（判官取 K 次中位数）· `--only <ids>`（只跑某些 fixture）· `--workers <n>`。
- **主流程**（对 `configs × fixtures × samples` 叉积并发）：载 fixture → 用变体模板渲染成 (system, user) → 调 API → 解析产物 → L1 确定性检查 → L2 判官(可选) → 落 `out/<name>/<fixture>.txt` + `report.md` + `stability.md`(多 rep 的 mean/sd)。
- **【通用、不动】**：config 解析 · 叉积并发 · `--force-variant` 变体隔离 · 多 rep 汇总 · report 结构。
- **【必须 customize】**：① fixture 载入+渲染（你的输入 contract）② L1 确定性检查内容 ③ L2 判官 rubric（可空）④ 产物 parser（跑 agent 时抽工具调用/动作，而非纯文本）。
- 单文件脚本 + JSON 配置即可，无重依赖，任何 OpenAI-compatible endpoint 能跑。

## ④ 评判 / 度量

- **确定性优先**：任何能不靠 LLM 客观判的性质，都用确定性检查——grep / substring / schema 校验 / label 精匹配 / tool-call 匹配 / 字节级比对。**这是破噪音的关键**，让你能廉价地多轮跑、把候选真正分开。
- **LLM 判官只补"确定性够不着的语义残差"**：faithfulness / 是否编造源里没有的东西 / 遵循度。**必须喂 ground-truth 源**让它能指认无据断言；要求结构化输出；**parse 失败按失败处理**。
- **L2 可以为空**：确定性检查已覆盖（如分类器有 gold label）就别硬加判官。
- **判官噪音大（单次 sd≈2），永远别 n=1**：每格 ≥3 reps（关键对比 ≥5），比"稳定分离"而非"单次胜负"；subset/superset 交叉验证识破假回归（superset 不该比它的 subset 在同输入上更差）。
- **收敛判据**：确定性层**一个不能退**（它是回归护栏）；LLM 层中位数**稳定高于 baseline** 且 sd 没掩盖差异，才算 win。

## ⑤ 装配 + 诚实迭代

- **顺序**：挖 2-3 个真实判别样例 + 1-2 个护栏样例 → 写确定性断言（逐字对着源核实）→ 写判官 rubric → 跑 baseline 建分 → 此后每版改动只需换变体重跑、比汇总表。
- **谁来建**：**设计（选哪些样例 / 定哪些度量 / 护栏测什么）是你的核心判断，不能外包**；脚手架体力活可派 sub-agent，但 **parser / 度量必须你亲自对着 ground-truth 校验**——parser 认错结构会静默数错关键指标。
- **一次只改一个关注点**；改完 diff 看信息丢没丢、范围有没有意外扩大。
- **诚实收手**：稳定改进 + 护栏不退 + diff 证明信息保全 → 上线。否则——都在噪音内 / 都带真代价 → **诚实说"没赢"，保留 baseline，把有效但有代价的候选留作 experimental（架上备用），不设默认。**

## 通用性：骨架通用，内容按对象实例化

**通用不变**：测下游输出而非文本 · 真实挖样本 + 两类样例 · 配置驱动并行 runner + 单接入点 + 多轮抽样 · 确定性优先 + 判官只补残差 · 诚实收敛。

**按对象实例化的**：
- **确定性检查的内容**随域重写：distiller = 该保留的行号/子串在不在、压没压缩；agent prompt = 有没有调对工具/做对改动/该问澄清时问没问；工具描述 = 选对工具、参数对、少误触发；分类器 = 标签精匹配。
- **判官的有无**：输出可精确比对时（分类器）判官可为空。
- **"测最终目标行为，不只测中间产物"**：distiller 有"笔记 → 下游 agent 决策"的二跳，改了笔记还要看下游决策变没变；但**终点型**提示词（分类器 / agent system-prompt / 工具描述本身就是终点）没有独立下游，这一步退化。通用说法是"测最终目标行为"，二跳回测只是 distiller 这类**多跳**对象的实例。

## 用 /pi-consult 当提示词候选顾问（有多模型时——可选，但用法有硬纪律）

顾问的本质是**提示词的建议者**。它是可选的候选生成 / 复核方式，但下面几条不照做反而引入信息丢失：

- **各家候选分别跑，别急着整合。** 顾问出来的每份候选 prompt，**各自丢进 bake-off 单独跑**，看谁实测最好——先别把几家的话揉成一份，融合往往两头不到岸。整合是**最后一步，且由你做**。
- **每份候选都要拆解查信息丢失。** 顾问（尤其爱重写的模型）给的 prompt，逐条对着**当前版 / 原版** diff：**有没有丢掉核心的 / 原有的限制**（如 distiller 的"不能下判断"这类约束）。优化一个点时顺手删掉别的约束，是最常见、最隐蔽的损失。
- **发现漏了，续跑那家的 session 让它辩护 + 修。** 用**同一个 `--session-id` 续跑（resume）**对应顾问，把"你这版丢了 X 约束"摆给它，让它**辩护是不是真漏了、并给出既补回 X 又不破坏新改动的修法**——别自己脑补它的意图。（续跑靠 /pi-consult 默认留的 transcript：同 `--session-dir` + `--session-id` 再发一条消息即接上原上下文。）
- **弱执行模型（如 deepseek-v4-pro）只取 idea，别让它自己写整份 prompt。** 它们分析力强、但重写整份时极易漏掉别的东西；**由你（或你派的 agent）把它的 idea 增量整合进模板**，整合完再 diff-审。
- **闭环加深**：把实验结果回灌给顾问逼第二轮更狠的招；判官太噪时也让它们出确定性度量方案。
- 每份建议采纳前用 /no-flattering 拷打其前提（引源真不真、把"一致"当"为真"没有）。
