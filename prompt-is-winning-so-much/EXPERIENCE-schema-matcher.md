# 经验记录：schema-matcher 提示词的打磨与验证（2026-08-04）

> 性质：经验笔记，不是提示词，不进入任何系统提示。记录一次「提示词精致化」工作的过程与教训，供日后打磨其他提示词时参考。

## 背景

`.pi/APPEND_SYSTEM.md`（六对图式的运行时行为调节器）对图式理论的解释不够精致与完整。参照 `general-prompt`（七层图式闭合）与 `abstraction-analyst`（理解记录方法论）重写，沉淀为 `schema-matcher/` skill，并经多轮子代理测试后替换回原位置。

## 流程（可复用）

1. **诊断先于改写**。先列出原提示词的具体缺陷清单（理论骨架未显式化、判断无操作化、内部矛盾、坏句子……），每条缺陷对应一个改写动作，不接受"整体润色"。
2. **从同类优质文件汲取结构养分**。`abstraction-analyst` 的「术语先定义→检验标准→操作步骤→失败处置表」骨架直接可移植；好提示词的共性是定义闭环，不是文采。
3. **锁定记号，消除自由度**。凡是要求模型重复书写的格式（量级、锚点、沿用），必须锁死为枚举形式并明写"不得使用变体"。自由格式在单次执行中看不出问题，多轮执行必然漂移。
4. **零上下文子代理测试是性价比最高的验证手段**。新实例只凭文件本身执行，能同时验证"提示词自包含性"和"规则可执行性"。测试要铺广：模糊提问、自然语言转向、跨领域（创意/事实/医疗）、冲突需求、元层级追问、多轮错配重判。
5. **测试发现的缺口要区分根源**。漂移可能源于模型不服从（需加强措辞），也可能源于规范本身不闭合（如锚点记号只有"居中·锚点"一种写法，而锚点表有四个位置）——后者改规范，前者改措辞，不能混淆。
6. **部署留备份**。替换原文件前 `.bak` 备份，一秒的事，回滚零成本。

## 具体教训（本次实测）

- 量级记号「微/中/重」不写死，三轮测试内就漂出「微偏」「重偏」等变体；写死后三个子代理七轮零漂移。
- 「显式输出判断」与「不暴露理论」看似矛盾，调和方案是分层：判断块显式、正文术语隐身。
- 子代理测试暴露的唯一规范缺口（锚点记号不闭合）恰好在示例文件里已有正确答案（examples.md 用了"构成·锚点"）——**示例先行能提前验证规范的可写性**。
- 弱模型（K2.6）验证仍是空白：子代理无模型选择能力，跑的是同模型。真正的弱模型泛化验证只能人工粘贴测试，话术已备好（模糊提问→"太长了说重点"→"有没有例外"，观察锚点停留、增量重判、已确认判断不推翻三点）。
