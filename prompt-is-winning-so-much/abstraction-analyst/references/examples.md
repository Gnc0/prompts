# 完整示例

三个示例分别覆盖三种典型情形：模糊需求的首次定位，需求变化时搁置清单如何起作用，以及修改类任务中搁置清单如何划定修改边界。

---

## 示例一：模糊需求的首次定位

**输入。** 用户发来一份二十页的产品方案文档，附言："帮我看看这个方案，下周要上评审会。"

**第 1 步，接收。** 通读文档与附言，不归类。

**第 2 步，分析话题结构。** 话题是"产品方案评审"，其结构包含两组部分：方案内部（目标、功能范围、技术路径、排期、风险），方案外部（评审会的决策标准、评审者构成、通过条件）。附言中唯一的时间信息指向评审会，因此外部部分与本次需求很可能相关，需要展开；方案内部各章只需知道其内容分布。

**第 3 步，定位需求。** 候选定位有两个。定位一：指向内部构成，即逐页审查方案的内容质量。定位二：指向情境适用，即判断方案在评审会上能否通过、哪里会被攻击。支持定位二的依据是：附言强调的是评审会而非方案本身，且用户没有指出任何具体章节。支持定位一的依据不存在。因此采用定位二，但置信度不充分，保留一个不确定之处。

**第 4 步，填写搁置清单。** 方案内部的细节问题（例如第十二页的排期矛盾、第十五页的技术风险表述含糊）与"能否通过评审"暂不直接相关，记入搁置清单。

**产出的理解记录：**

```markdown
## 理解记录
1. **话题结构**：产品方案评审。相关部分：方案内容（内部）与评审决策标准（外部）。
2. **需求位置**：指向［情境适用］——方案在评审会上的通过性，以及最可能被攻击的点。
   - 依据："下周要上评审会"是附言中唯一的强调信息；用户未指向任何具体章节。
   - 不确定之处：用户可能同时需要内容层面的逐页意见。澄清问题：
     "重点是评审会上怎么通过，还是也需要逐页的内容修改意见？"
3. **搁置清单**：
   - 第十二页排期矛盾｜不影响通过性判断本身，但可能成为评审攻击点｜若确认攻击点涉及排期则启用
   - 第十五页技术风险表述含糊｜同上｜若评审者中有技术负责人则启用
4. **回应建议**：概念范围＝评审通过性；信息密度：详细展开＝最可能的三个攻击点及应对；
   简要提及＝方案整体结构。
```

注意第 3 步与搁置清单的衔接：排期矛盾被搁置，但启用条件已经写明。如果用户澄清"评审主席最看重交付时间"，该条立即从搁置清单转入回应材料，不需要重读全文。

## 示例二：需求变化时搁置清单如何起作用

**输入。** 对话中段。用户此前问"我们的微服务架构为什么这么慢"，分析者把需求定位为［内部构成］（调用链的延迟来源），并给出了逐项延迟分析。用户回复："我不是问这个——我是想知道当初为什么选微服务，现在要不要退回单体。"

**识别失败。** "我不是问这个"表明定位的需求不是用户真实的需求。此前的定位是假定（假定用户要做性能优化）；用户实际的需求指向［外部关系］：架构选型的历史理由，以及当下是否应当放弃这一选型。

**只重新计算受影响的部分：**

1. 话题结构不变，仍是该系统的架构，不需要重建。
2. 需求位置重新定位：由［内部构成·调用链］改为［外部关系·选型理由与去留条件］。依据是用户原话直接给出了新位置。
3. 查询搁置清单。第一轮分析时被搁置的信息中，有三条的启用条件此刻已经满足："团队只有四人""用户说维护成本越来越高""用户三次追问部署复杂度"。这三条与选型去留直接相关，从搁置清单转入回应材料，成为新回应详细展开的部分。第一轮的调用链延迟分析则整体转入搁置清单，启用条件写为："去留判断落定之后，如需优化细节则启用"。
4. 用户已经确认过的理解（系统拓扑、团队规模等事实）保留，不推翻。

**本例说明的要点。** 没有搁置清单时，"我不是问这个"意味着此前接收的信息全部作废，只能从头理解。有搁置清单时，需求变化是一次有记录的重新划分：哪些信息从搁置清单转入回应材料、哪些从回应材料退入搁置清单，逐条可以追溯。

## 示例三：修改类任务中搁置清单划定修改边界

**输入。** 对话中段。分析者此前按一套分层设计规范（文档分性质、模型、论证三层）起草了一份回路设计文档：八条性质、五个组件、三段论证，内容方向已在上一轮审议中获用户逐条确认。用户审阅后回复："优化你的语言表达。要求不过度压缩，能够把问题讲明白，不使用任何修辞手法（严禁比喻），不用任何杂糅概念，正常使用语言与概念。"

**第 1 步，接收。** 收下文档与指令。指令的宾语是语言表达；指令没有提及任何一条性质的方向、任何组件的划分、任何章节格式。

**第 2 步，分析话题结构。** 这份文档由三层组成：内容层（八条性质的规范方向、五个组件的义务划分、论证的结论）、结构层（章节与字段格式，来自设计规范）、表达层（语言与措辞）。指令的四项要求——不过度压缩、把问题讲明白、不使用修辞手法、不用杂糅概念——全部落在表达层。

**第 3 步，定位需求。** 需求指向［内部构成·表达层］，并排除另外两层。依据：指令的宾语是"你的语言表达"；四项要求都是对语言的要求；内容层的方向在上一轮已获用户逐条确认，本轮无新意见。不确定之处：无。

**第 4 步，填写搁置清单。** 修改类任务的搁置清单里，除无关信息外，还要登记"不能动的合法内容"，每条写明判断依据与启用条件。

**产出的理解记录：**

```markdown
## 理解记录
1. **话题结构**：设计文档的表达修订。文档分内容层、结构层、表达层；需求全部落在表达层。
2. **需求位置**：指向［内部构成·表达层］。
   - 依据：指令宾语为"你的语言表达"；四项要求均为语言要求；内容层上轮已获逐条确认。
   - 不确定之处：无。
3. **搁置清单**：
   - 设计规范的正式字段与符号（frame、root、组件去向标注、⊨）｜体系词汇，不是表达缺陷｜用户要求废弃该规范时启用
   - 用户原话引入的词（如"落地形式"）｜出现在用户裁决原文中，删除它等于改写用户的规范决定｜用户本人改用新说法时启用
   - 项目内已确立用语（登记簿名称、回路等）｜已在项目文档中固定使用，超出本次对象范围｜用户要求重命名项目术语时启用
   - 内容层与结构层（八条性质的方向、组件划分、章节格式）｜需求不在此层｜用户对内容或结构提出意见时启用
4. **回应建议**：概念范围＝表达层；信息密度：详细展开＝违规表达的识别与替换；简要提及＝内容与结构保持原案。
```

**执行。** 修改按四类进行，每一处写明替换前后：

- 删比喻词，给出正常表达（"迁移窄门"改为"迁移须经确认并迭代"；"机器指纹"改为对事实的直接陈述）。
- 删自造压缩词（"双落地"改为"两种落地形式"；"画像"改为"分布"；"靶点"改为"清单项"）。
- 清理中英混排（"未 discharge 的义务"改为"未履行的义务"）。
- 删最高级断言，并检查删除后论证是否仍成立（"依赖最小"改为"不依赖其可信性，未校准数据仍可用作线索"——论证仍成立，因为主张的是"不依赖"这一事实，不是排序）。

另有一类反向操作：展开过度压缩处。单句压缩的规范陈述展开为完整句——满足标准是什么、违反情形是什么、检查内容逐项写明。删修辞腾出的位置由展开的陈述填充，而不是留下更短的电报体。

判断一个词该不该删的操作标准：区分该词的来源。体系正式词汇与用户原话进入搁置清单；分析者自己引入的比喻、压缩词、最高级进入修改范围。

**检验。** 用户回复"正确！"——定位由用户的后续反应确认（第一节标准 1）。

**本例说明的要点。** 修改类任务中，搁置清单的作用是划定修改边界，防止"用户要求改一处，助手重写全文"：被搁置的不只是无关信息，还包括不能动的合法内容。判断边界的可操作标准是来源——谁的词、哪个体系、哪一层。本例还说明了语言纪律与信息密度的配合：修辞删掉之后，需求所在的位置由展开的陈述占据，文档没有因此变得更短或更空。
