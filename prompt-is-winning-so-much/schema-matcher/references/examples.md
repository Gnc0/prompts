微服务架构的核心想法是：把一个庞大的应用拆成一组小而独立的服务，每个服务只负责一块明确的业务（比如用户、订单、支付），各自独立开发、部署、扩容，服务之间通过网络接口协作。

可以用一个类比来理解：传统的单体架构像一家所有工序都在同一个车间里的大工厂，改一条产线要全厂协调；微服务则像一组专业化的小作坊，各自独立运转，靠标准化接口对接。

它的吸引力主要来自三点：

- 独立性：单个服务出问题或要升级，不必牵动整个系统
- 灵活性：不同服务可用不同技术栈，按各自负载单独扩容
- 组织匹配：小团队各自负责一个服务，职责边界清晰

代价同样明显：服务间通信带来延迟与故障点，数据分散后一致性更难保证，部署、监控、排错的运维复杂度显著上升。

一句话概括：微服务是用运维与协作的复杂度，换取系统的灵活性与可演进性。是否值得，取决于系统规模和团队能力。

- 微服务 = 把一个大应用拆成多个独立小服务，各自部署、靠接口通信。
- 好处：灵活、可独立扩容、团队边界清晰。
- 代价：运维、通信、数据一致性都更复杂。
- 一句话：用复杂度换灵活性，小项目通常不值得。

有，以下情况通常不适合：

- **系统小、业务简单**：单体就够用，拆分纯属自增复杂度。
- **初创期、需求未定型**：服务边界会反复推翻，返工成本极高。
- **团队小、缺运维能力**：微服务依赖自动化部署、监控、DevOps 配套，没有这些就是负担。
- **强一致、事务耦合重的业务**：跨服务数据一致性很难做（如核心账务、库存强扣减）。
- **对延迟极敏感的模块**：网络调用替代进程内调用会放大延迟。
- **领域边界划不清**：强行拆分只会得到一个"分布式单体"，比单体更糟。

判断标准一句话：当拆分带来的协调与运维成本，大于它解决的复杂度时，就不该用微服务。

**本例说明的要点。**

1. 第 1 轮演示锚点：无信号维度（中心↔边界、精确↔召回、构成↔调节）停在锚点，不凭偏好投射偏移。
2. 第 2 轮演示错配处置表："太长了／说重点"→ 压缩↔展开单维重判，其余沿用；强偏压缩触发搁置行，且判断块自身从简。
3. 第 3 轮演示增量重判与"已确认判断不推翻"：只重判受影响的四个维度，用户第 2 轮确认的压缩偏好跨轮保留，正文仍逐条压缩。
